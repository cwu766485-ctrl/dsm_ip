# ZU15EG Bring-Up

This folder contains public, source-only bring-up notes for validating the DSM
IP on an XCZU15EG MPSoC board. The local vendor project used for first
bring-up targets `xczu15eg-ffvb1156-2-i`.

Private board schematics, board files, vendor examples, license files, server
addresses, and local capture data must stay outside the public repository.

## First Board Goal

Build the smallest PS-to-PL validation loop:

```text
Zynq UltraScale+ PS
-> AXI DMA MM2S
-> DSM IP s_axis
-> interpolation frontend
-> DSM core
-> Fs/4 DUC
-> rf_valid / rf_signed
-> ILA probes
```

The first board pass does not need an external DAC or high-speed connector. The
goal is to prove that software can configure the IP, stream known I/Q samples,
and observe expected PL activity with ILA.

The next target architecture moves DPD control from PC/XSDB toward PS-side
software:

```text
PS Linux / bare-metal C / Python
-> calibration / ML / optimization
-> AXI-Lite writes DPD coefficients or LUT entries
-> AXI DMA sends I/Q samples
-> PL DPD + interpolation + DSM
```

Linux/PYNQ boot was not available during local bring-up, so the current
preferred path is Vitis bare-metal control. The retained PS Linux helper under
`ps_linux/` is optional. The bare-metal smoke app under `baremetal/` is the
main path for PS-controlled DPD and DMA validation.

## Recommended Configuration

Start with the lightest compiled configuration:

```text
ALGORITHM   = 2   EFDSM 1-bit
INTERP_MODE = 0   bypass
DUC_MODE    = 0   fixed Fs/4
Clock       = 100 MHz
```

After the baseline works, test the heavier routed-OOC configurations:

```text
ALGORITHM=6,  INTERP_MODE=4
ALGORITHM=12, INTERP_MODE=4
```

These two combinations already have retained ZU15EG routed OOC evidence in
`docs/evidence/ooc`.

## Register Smoke Sequence

Software should perform this minimum sequence:

1. Read `VERSION`, `ALGORITHM`, `DUC_MODE`, and `INTERP_MODE`.
2. Write `CTRL=0x00000004` to clear counters and sticky status.
3. Write `CTRL=0x00000002` to issue software reset.
4. Write `CTRL=0x00000001` to enable the IP.
5. Start AXI DMA MM2S with a known packed I/Q vector.
6. Poll `INPUT_SAMPLE_COUNT`, `FRONTEND_SAMPLE_COUNT`, `OUTPUT_SAMPLE_COUNT`,
   `INPUT_STALL_COUNT`, `INPUT_FRAME_COUNT`, and `ERROR_STATUS`.

When the PL clock is generated by the Zynq UltraScale+ PS, run the generated
`psu_init.tcl` sequence before using ILA:

```tcl
connect -url tcp:127.0.0.1:3121
source <project>.gen/sources_1/bd/design_1/ip/design_1_zynq_ultra_ps_e_0_0/psu_init.tcl
targets -set -filter {name =~ "PSU"}
psu_init
psu_ps_pl_isolation_removal
psu_ps_pl_reset_config
```

Without PS initialization, the bitstream can still program successfully, but
the debug hub may not be detected because `pl_clk0` is not running.

## ILA Probes

Probe these first:

```text
s_axis_tvalid
s_axis_tready
s_axis_tdata
s_axis_tlast
s_axis_tuser
rf_valid
rf_signed
dsm_valid
i_yout
q_yout
phase_acc_dbg
```

Expected first-pass behavior:

- `s_axis_tready` can toggle under interpolation backpressure.
- `INPUT_SAMPLE_COUNT` increments on accepted AXI-Stream samples.
- `FRONTEND_SAMPLE_COUNT` increments on samples accepted by the interpolation
  and DSM frontend.
- `OUTPUT_SAMPLE_COUNT` increments when `rf_valid` is high.
- `ERROR_STATUS` remains zero for a clean stream with `tuser=0`.

## Bare-Metal Control

Use `baremetal/src/dsm_dpd_baremetal_smoke.c` when Linux/PYNQ is unavailable.
The app performs the same core checks as the XSDB smoke:

- configures polynomial DPD coefficients,
- configures LUT DPD entries,
- starts AXI DMA MM2S with a generated packed I/Q vector,
- checks input, frontend, DPD, output, stall, error, and saturation counters.
- iterates MATLAB-exported polynomial/LUT DPD packages,
- combines MATLAB proxy EVM/SNDR with hardware saturation, clipping, stall,
  sticky error, correction-magnitude, and RF-slew proxy penalties,
- selects the lowest-cost package and leaves the selected DPD mode/package
  programmed in PL registers.

`matlab/dpd/export_dpd_coeff_header.m` generates
`baremetal/src/dpd_coeffs.h` from the MATLAB AI-assisted DPD sweep. The C app
includes this header when present, so MATLAB calibration output can directly
feed the PS bare-metal control program. This is the first complete PS-side
AI-assisted calibration loop; it does not require PS Linux.

## DPD Board Smoke

After the DPD-enabled bitstream is generated, use Vivado Address Editor to find:

- AXI-Lite base address of `dsm_ip_0`
- AXI-Lite base address of `axi_dma_0`

Generate the DMA source vector:

```powershell
python .\fpga\zu15eg\scripts\pack_p0_iq_for_dma.py --limit 4096
```

Then run the XSDB smoke through JTAG:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\fpga\zu15eg\scripts\run_xsdb_dpd_dma_smoke.ps1 `
  -DsmBase 0xA0000000 `
  -DmaBase 0xA0010000
```

Replace the two base addresses with the values from the local block design.
Use `-DpdMode poly`, `-DpdMode lut`, or `-DpdMode bypass` to select the DPD
datapath mode used by the smoke test.
The smoke script:

- optionally programs `top.bit` from the local hardware project,
- runs `psu_init.tcl` when available,
- writes and reads back the selected DPD polynomial or LUT registers,
- enables the selected DPD mode,
- starts one AXI DMA MM2S transfer,
- checks input, frontend, DPD, output, stall, and error counters.

Use `-SkipProgram` when the bitstream is already programmed. Use `-PrintOnly`
to check paths and environment variables without launching XSDB.
Use `-SkipPsuInit` only when PS clocks, DDR, and PS-PL isolation have already
been initialized; otherwise AXI-Lite and DMA accesses can time out.

For a repeatable board regression, run:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\fpga\zu15eg\scripts\run_zu15eg_baremetal_regression.ps1
```

This performs the full local sequence:

```text
rebuild bitstream
-> export XSA
-> build bare-metal ELF
-> program bitstream
-> launch ELF
-> read and check DSM counters
-> generate PASS/FAIL log
```

During interactive debug, reuse existing artifacts to shorten runtime:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\fpga\zu15eg\scripts\run_zu15eg_baremetal_regression.ps1 `
  -SkipBitstreamBuild `
  -SkipXsaExport `
  -SkipElfBuild
```

Regression logs are written under `fpga/zu15eg/out/`, which is intentionally
ignored by git.

The local validated address map is:

```text
dsm_ip_0  = 0xA0010000
axi_dma_0 = 0xA0020000
```

The DPD and spectral-monitor enabled board flow requires
`C_S_AXI_ADDR_WIDTH=8` on `dsm_ip_0`.
Older local designs with a 6-bit or 7-bit AXI-Lite address port can read the
legacy registers but cannot access the full DPD/monitor map through `0x8C`.

The current one-command regression has also been run with the PS-side
calibration loop enabled. In the latest quick board run, the final counter
check reported `DPD_CTRL=0x00000002`, indicating that the loop selected and
retained LUT DPD mode after evaluating the exported packages. The run completed
with 4096 input/frontend/DPD/output samples, zero input stalls, zero sticky
errors, and zero DPD saturation.

## First Hardware Evidence

The first local ZU15EG pass completed these checks:

- JTAG detected `xczu15_0` and `arm_dap_1`.
- A vendor GPIO bitstream programmed successfully.
- DSM+AXI DMA+ILA bitstream generation completed with routed timing clean.
- `top.bit` and `top.ltx` programmed successfully.
- After `psu_init`, Hardware Manager detected one ILA with 10 probes.
- AXI-Lite reads returned `VERSION=0x00010000`, `ALGORITHM=2`,
  `DUC_MODE=0`, and `INTERP_MODE=0`.
- A 4096-word DMA MM2S transfer completed with matching
  `INPUT_SAMPLE_COUNT`, `FRONTEND_SAMPLE_COUNT`, and `OUTPUT_SAMPLE_COUNT`;
  `INPUT_STALL_COUNT=0` and `ERROR_STATUS=0`.

The BD template configures AXI DMA `c_sg_length_width=23`. If an older
bitstream uses the default 14-bit length field, keep simple-mode transfers at
or below `0x3FFF` bytes.

## DPD Hardware Evidence

The DPD-enabled ZU15EG board smoke completed these checks:

- The local DSM IP was rebuilt with `C_S_AXI_ADDR_WIDTH=8`.
- Vivado programmed the new `top.bit` and `top.ltx`.
- XSDB ran `psu_init.tcl` and accessed the DSM and AXI DMA registers.
- DPD coefficient readback passed:
  - `DPD_C1=0xFFFB4009`
  - `DPD_C3=0xF1A41F6F`
  - `DPD_C5=0xDE503A39`
  - `DPD_CTRL=0x00000001`
- A 4096-word DMA MM2S transfer completed:
  - `INPUT_SAMPLE_COUNT=0x00001000`
  - `FRONTEND_SAMPLE_COUNT=0x00001000`
  - `DPD_SAMPLE_COUNT=0x00001000`
  - `OUTPUT_SAMPLE_COUNT=0x00001000`
  - `INPUT_STALL_COUNT=0x00000000`
  - `ERROR_STATUS=0x00000000`
  - `DPD_SATURATION_COUNT=0x00000000`

The LUT DPD mode was also rebuilt into the ZU15EG bitstream and smoke-tested:

- `DPD_LUT0=0x00004000`
- `DPD_LUT15=0x00004000`
- `DPD_CTRL=0x00000002`
- A 4096-word DMA MM2S transfer completed with matching input, frontend, DPD,
  and output sample counters.
- `INPUT_STALL_COUNT=0x00000000`
- `ERROR_STATUS=0x00000000`
- `DPD_SATURATION_COUNT=0x00000000`

Useful debug lessons:

- If `DPD_C1` reads back as zero after a write, the board is probably running
  an old bitstream or the DSM IP still has a 6-bit AXI-Lite address port.
- XSDB target discovery can be less reliable for PL programming than Vivado
  Hardware Manager on this setup. The retained flow programs the bitstream
  with Vivado and uses XSDB for PS init, AXI-Lite, and DMA.
- The rebuilt design closes routed implementation on the local
  `xczu15eg-ffvb1156-2-i` project, but Vivado reports DPD DSP pipelining
  warnings. These warnings are a future power/timing optimization item.
- If XSDB shows no targets while Windows only enumerates FTDI serial ports,
  reinstall the Xilinx cable drivers from an administrator shell, then unplug
  and reconnect USB/JTAG before rerunning target discovery. If target
  discovery is still empty, check whether the FT4232H appears only as generic
  FTDI VCP ports. The board schematic shows onboard USB-to-JTAG through
  FT4232H plus an external JTAG connector `J2`, and the vendor Vitis scripts
  expect a `Xilinx HW-U1-VCU1525 FT4232H` cable. Empty target discovery after
  driver installation usually means the FT4232H EEPROM/driver binding is not
  being recognized as a Xilinx/Digilent cable, or the main board/JTAG path is
  not powered. Use the vendor-provided USB-JTAG driver/EEPROM setup if
  available, or connect a known-good Xilinx/Digilent JTAG adapter to `J2`.
- On the local board, the Type-C connector `J1` enumerated the onboard FTDI
  interface and lit the nearby LED, but Vivado/XSDB target discovery remained
  empty through that path. Using the external `J2` JTAG path with a Digilent
  JTAG-SMT2 exposed `xczu15`, `arm_dap`, PL, PMU, RPU, and APU targets.

## Editor Diagnostics

The multibit DSM wrappers instantiate `dsm_core_multibit` from
`rtl/dsm/multibit/dsm_core_multibit.sv`. That source is present in
`rtl/filelist_p0.f`, so Vivado/XSim compilation uses the correct dependency
order. If VS Code or a language server reports `unknown module
dsm_core_multibit` while opening a wrapper file directly, treat it as an
editor-only filelist configuration issue. Configure the editor to parse the
project filelist, or run the regression scripts as the source of truth.
