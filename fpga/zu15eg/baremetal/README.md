# ZU15EG Bare-Metal DSM/DPD Smoke

This folder contains the first Vitis bare-metal control application for the
DSM TX IP. It translates the previously validated XSDB smoke flow into C:

```text
PS bare-metal C
  -> Xil_Out32 / Xil_In32 writes DSM AXI-Lite registers
  -> XAxiDma simple-mode MM2S sends packed I/Q
  -> PL DPD + interpolation + DSM datapath runs
  -> C app checks counters and prints PASS/FAIL over UART/JTAG console
```

The goal is to avoid relying on Linux/PYNQ while still proving PS-controlled
PL datapath operation.

## Source

| Path | Purpose |
|---|---|
| `src/dsm_dpd_baremetal_smoke.c` | Bare-metal DPD polynomial/LUT calibration and DMA smoke |
| `src/dpd_coeffs.h` | MATLAB-exported DPD coefficient, LUT, and proxy-score packages |
| `scripts/build_baremetal_smoke.ps1` | Builds the Vitis standalone platform and A53 ELF |
| `scripts/build_baremetal_smoke.py` | Vitis 2024.1 Python API build script |
| `scripts/run_baremetal_smoke.ps1` | Downloads and starts the ELF through XSDB |
| `scripts/run_baremetal_smoke.tcl` | XSDB target, PS init, and ELF launch script |

## Expected Hardware

- Local ZU15EG Vivado project with the DSM IP at `0xA0010000`.
- AXI DMA simple-mode instance exported in the XSA.
- DSM IP AXI-Lite address width set to 8 bits so the DPD registers and monitor
  registers through `0x8C` are accessible.
- PS initialization and PL clocks generated by the Vitis platform.

## Vitis 2024.1 Build

Export the hardware platform from the local Vivado project:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\fpga\zu15eg\scripts\export_hw_platform.ps1
```

Build the standalone A53 application:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\fpga\zu15eg\baremetal\scripts\build_baremetal_smoke.ps1
```

The script uses the Vitis 2024.1 Python API because the installed Vitis
Embedded flow does not support the older classic XSCT platform/app commands.
The generated ELF is:

```text
fpga/zu15eg/out/vitis_baremetal/dsm_dpd_baremetal_smoke/build/dsm_dpd_baremetal_smoke.elf
```

Vitis may print Windows PATH noise about missing MicroBlaze or `gnuwin`
folders after the build. Treat the build as passed only when the script exits
with code 0 and prints the final ELF path.

## Vitis Run

Open the PS UART terminal first if the board exposes it over a USB serial
port. Then launch the ELF:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\fpga\zu15eg\baremetal\scripts\run_baremetal_smoke.ps1
```

The run script optionally programs `top.bit`, runs `psu_init.tcl`, resets
Cortex-A53 #0, downloads the ELF, and starts it. Application prints appear on
the PS UART through `xil_printf`; they do not automatically appear in the XSDB
console.

If XSDB lists no targets, install the Xilinx cable drivers from an elevated
PowerShell or administrator command prompt:

```powershell
D:\Xilinx\Vitis\2024.1\data\xicom\cable_drivers\nt64\install_drivers_wrapper.bat
```

Unplug and reconnect the USB/JTAG cable after driver installation, then rerun
`scripts/xsdb_list_targets.tcl`.

## Compile-Time Defaults

The app assumes these defaults:

```c
#define DSM_BASEADDR 0xA0010000U
```

For older BSPs, the AXI DMA lookup can use `XPAR_AXIDMA_0_DEVICE_ID`. For
Vitis 2024.1 SDT BSPs, the app falls back to the AXI DMA base-address macros
such as `XPAR_XAXIDMA_0_BASEADDR`.

Override `DSM_BASEADDR` in the application compiler settings if the local
Address Editor assigns a different value:

```text
-DDSM_BASEADDR=0xA0010000
```

## Expected Output

The app first iterates all exported DPD packages in polynomial DPD mode and LUT
DPD mode. Each package has a MATLAB-exported proxy EVM/SNDR score. The board
run adds hardware penalties from DPD saturation, clipping, sticky error,
correction-magnitude, RF-slew, fixed-bin spectral adjacent proxy, and
AXI-Stream stall counters.

After package evaluation, the app runs a small PS-side coordinate-search loop
around the best polynomial package. It perturbs the fixed-point Q2.14 `C1`,
`C3`, and `C5` coefficient words, runs the DMA/datapath for each candidate,
reads the same hardware counters, and accepts a candidate only when its cost is
lower. The final selected configuration can therefore be either:

- an exported polynomial package,
- a searched polynomial coefficient set,
- or an exported LUT package.

The final configuration is written back to PL registers and the stream is run
one more time so post-run counters reflect the selected DPD configuration, not
an intermediate search candidate.

Each package run should report:

```text
PASS DPD_CTRL
CAL_RESULT mode=<m> package=<n> evm_ppm=<score> sndr_mdB=<score> ...
PASS INPUT_SAMPLE_COUNT = 0x00001000
PASS FRONTEND_SAMPLE_COUNT = 0x00001000
PASS DPD_SAMPLE_COUNT = 0x00001000
PASS OUTPUT_SAMPLE_COUNT = 0x00001000
PASS INPUT_STALL_COUNT = 0x00000000
PASS ERROR_STATUS = 0x00000000
```

At the end it writes the selected package back to the DPD registers:

```text
SEARCH seed package=<n> step=<q214_step> rounds=<n>
CAL_SEARCH_RESULT package=<n> evm_ppm=<score> ...
SEARCH_ACCEPT coeff=<c> part=<real_or_imag> delta=<q214_step> ...
SELECTED mode=<m> package=<n> searched=<0_or_1> evm_ppm=<score> sndr_mdB=<score> cost=<score>
Re-running stream with selected DPD package to refresh final counters
PASS selected DPD package is retained in PL registers
```

This is the first PS-side AI-assisted calibration loop. The "AI-assisted"
boundary is the low-rate PS optimization/search engine; the PL remains a
deterministic fixed-point DPD, interpolation, and DSM datapath. This is still
a board-control smoke test. It does not prove external DAC/RF output or real
PA linearization without an observation receiver or measurement chain.
